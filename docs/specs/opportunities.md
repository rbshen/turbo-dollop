# Weekly Routine (the weekly opportunity agent)

**Naming (2026-10-18).** The page is called **Weekly Routine** everywhere a user sees it (nav label, page heading, browser tab title, empty and error text). The route stays `/opportunities`, and the files, API endpoints, tables and internal identifiers (`OpportunitiesTable`, `OpportunityRun`, `/api/opportunities`, `app/opportunities/`) keep the old name. This doc and the code comments still say "opportunity" for the data and the job.

Built 2026-10-11 (phase 1b); the daily flags (Phase 2b v1) were added 2026-10-12, see "Daily flags" below; the unlisted pool names' slim outcomes (scorecard step 1) the same day, see "Pool outcomes". Two frozen lists, **Momentum** and **Reversal**, built across the whole tracked universe from **stored data only** (no FMP call,
no LLM call, no live price), saved as a dated snapshot and shown on the read-only `/opportunities` page. Not part of the Overall score, the stage engine or any
nightly job: it only reads them. **Cron: enabled 2026-10-12** (Saturdays 4:00 AM server time, see "Cron status", below). Code: `scoring/opportunity_rules.py` (pure rules), `data/opportunity_data.py` (load, evaluate, persist, read),
`pipeline/weekly_opportunity_snapshot.py` (entry point), `GET /api/opportunities/*` in `core/main.py`, `frontend/app/opportunities/`.

## The rules (versioned: `RULES_VERSION = "2"`, rule ids end `.v2`)

`scoring/opportunity_rules.py::rules_hash()` is the sha256 of every id and threshold below (`rules_definition()`); each run stores it with `rules_version`.
**Change any threshold and bump `RULES_VERSION`**, so an old run is read against the rules it used.

**One list per ticker (rules v2, 2026-10-11).** The lists are opposite in nature, so they are mutually exclusive and **trend stage decides which one a ticker can be on**
(`scoring/opportunity_rules.py::assign_list`, the single router; `place()` returns the one placement). Established Advance (stage Advance for **more than**
`FRESH_ADVANCE_MAX_WEEKS` = 8 weeks) -> Momentum only. Decline, Base, a pending Advance (`pending_direction = advance`) or a **fresh** Advance (<= 8 weeks) -> Reversal only. Top
(unless it has a pending Advance), no fresh stage row, or an Advance of unknown age -> neither. An established Advance outranks a pending-Advance flag. Being assigned a
list is necessary, not sufficient: the list's own rules must still hit, and a ticker that fails them is NOT rerouted to the other list. A **Momentum** row whose chart would pass
the B2 price-structure test (the tier's own drawdown threshold) gets the **`deep_pullback` tag** instead of a Reversal listing (the case the later daily routine will use). The
"also on the other list" tag is gone. Enforced three ways: the router; `UNIQUE (run_id, ticker)` on `OpportunitySnapshotRow` (a ticker has one row per run, whichever list); and
`compute_run` refuses to write if a ticker ever lands on both, with tests over every stage x weeks x pending x tier combination.

**Gate, all tiers** (a ticker that fails it is on no list and not ranked): not delisted (`TickerScore.delisted_at`); the last daily bar is dated the as-of date
(and was written after that session's close, the bars cache's provisional-bar test); at least 12 months of bars; average daily dollar volume (close x volume,
last 50 sessions) at least **$25M**; SPY excluded. Reason codes: `excluded`, `delisted`, `no_bars`, `stale_bar`, `provisional_bar`, `short_history`, `illiquid`.

**Tiers.** *Quality* = stored Overall verdict **Pass or Strong Pass** (`QUALITY_VERDICTS`). *Momentum-only* = every other stock (Fail, incomplete, and **Pass with
caution**, which the preview also kept out of Quality although it is a label on a passing score: one constant to change). *ETF* = the ETF universe
(`load_etf_universe`). A leveraged fund (curated `LEVERAGED_ETF_FACTORS` plus a name test: "3X", "UltraPro") carries the `leveraged` tag and is ranked in its own
group.

**Ranked universe.** Momentum rank = `scoring/momentum.py::compute_momentum_ranking` (3, 6, 12 month composite) on the cached closes at the as-of date, over the
tickers that **pass the gate**, in three separate groups: the tracked stocks, the ordinary ETFs, the leveraged ETFs. The group sizes are stored (`ranked_universe`)
and drawn in the page footnote. (The preview ranked the 575 stocks before the liquidity floor; ranking after it moves each cut by a name or two.)

**List A, Momentum** (`A.momentum_trend.v2`): an **established** Advance (weeks in Advance > 8), MA slope > 0, Mansfield RS > 0 (the stored RS, vs SPY while `rs_benchmark` is SPY; the run stores the
benchmark), and `vs_ma_pct` strictly below the tier ceiling: **20** Quality and ETF, **15** Momentum-only. Momentum-only also needs weeks in Advance <= 52, 3 month
return <= 30%, 12 month return <= 150% and momentum rank in the **top quintile** (ceil(n/5) of the ranked stocks, exact integer arithmetic). ETFs also need the
**top third** of their own group (ceil(n/3)). Quality needs no rank. Any unknown input (no fresh stage row, no rank, no return) fails the rule it feeds.

**List B, Reversal.** `B2.price_structure.v2` (all tiers, **evaluated only for tickers whose stage puts them on Reversal**): drawdown from the 52-week high >= 20% (Quality, ETF) or >= 30% (Momentum-only); a higher low (the lowest
low of the last 126 sessions is at least 15 sessions old and the last 15 sessions' lowest low is above it); weekly close above its 10-week SMA; the 30-week EMA slope
above its value 4 weeks earlier and >= -2%. `B1.base_or_pending_advance.v2` (Quality only): stage Base, or a pending Advance. `B3.entry_signal.v2` (Quality only): a
Warren `blue_up`/`yellow_up` or a BB+RSI event dated in the last 10 sessions **and** stage Decline or Base. Each rule keeps its own id on the row (`rule_ids_json`).

**B3 coverage.** Warren, BB+RSI and Liquidity Zones run only for the monitored lists (`E<n>` and `ETF`). `signal_status` per ticker: `fired` (an event in the
window: a fact whether or not the ticker is still monitored), `no_signal` (monitored, nothing fired), **`not_covered`** (not monitored, nothing fired: the signal
jobs never looked, so it is never shown as "no signal"). Stored on every Quality row; the Reversal table shows a "Signals not covered" tag; the run summary stores
`quality_not_covered` of `quality_total`.

**Tags** (stored in `tags_json`, never filters): `late_trend` (weeks in Advance >= 52), `leveraged` (2 or 3), `held_back_by_moat` (blended Fundamentals >= 70, Overall
< 70: only the Moat multiplier does it), `why_not_quality` (Momentum-only stocks: the raw stored Overall verdict, the steps below the pass line, the incomplete
steps, the moat; the page draws "May not pass", never "Fail"), `deep_pullback` (a Momentum row that passes the B2 chart test), `signal_status` (Quality), `market` (the latest `MarketBreadthSnapshot`
on or before the as-of date: % above 50/200-day SMA, net new highs) and `sector` (the sector ETF's stage and momentum rank, the sector's breadth snapshot).

## Tables (new, insert-only; no existing table changed)

`OpportunityRun`: `kind` ("weekly"), `as_of_date`, `last_bar_date`, `universe_size`, `rules_hash`, `rules_version`, `score_formula_version`, `weights_version`,
`created_at`, `summary_json` (counts per list/tier/rule_id, ranked-universe sizes, gate drops, stale stage and score row counts, market context). Unique on
`(kind, as_of_date)`. `OpportunitySnapshotRow`: `run_id`, `list_name` (momentum/reversal), `ticker`, `tier`, `list_order`, `rule_ids_json`, `tags_json`, and a frozen copy
of the inputs (`overall_score`, `steps_score`, `overall_verdict`, `weinstein_stage`, `vs_ma_pct`, `ma_slope_pct`, `mansfield_rs`, `momentum_rank`, `close`, `atr`
(Wilder 14), `adv_usd`, `sector`, and `inputs_json` for the rest: step scores and verdicts, moat, weeks in Advance, 3/12 month returns, drawdown, B2 parts, signal
status, exchange). Unique on `(run_id, ticker)`: a ticker has one row per run, on one list. `TickerScore` and `TrendAnalysis` are overwritten nightly, which is why
the inputs are copied.

**Registry and backup.** Both are **KEEP** in `data/ticker_data_registry.py` (`opportunitysnapshotrow` in `REGISTRY`; `opportunityrun` has no ticker column, so it is in
`KEEP_NON_TICKER_TABLES`): the wipe never touches them. The nightly backup (`pipeline/backup_db.py`) copies the whole database with sqlite's backup API, so both tables
are in it with no change (checked: no table list anywhere in that script).

## The job

`uv run python -m pipeline.weekly_opportunity_snapshot [--as-of YYYY-MM-DD] [--force] [--dry-run]`, run from `backend/`. As-of defaults to the last completed XNYS
session. A rerun for an existing `(weekly, as_of)` is a no-op (and does not even compute); `--force` deletes that run and its rows and inserts the new ones in one
transaction (a failed insert leaves the old run intact); `--dry-run` computes and prints the counts, writes nothing. Bars are read in chunks of 60 tickers
(`CHUNK_SIZE`); only the closes of gate-passing tickers are kept for the ranking. First run on the live database: about 12 s, peak RSS about 173 MB (the bare interpreter
and pandas are about 115 MB of it). The run **refuses** (raises, writes nothing) when fewer than 90% of the gate-passing tickers have a Weinstein row computed from the
as-of bar (`MIN_FRESH_STAGE_SHARE`): the nightly stage job has not caught up and the lists would silently omit every stage-dependent name. A stage row not dated the
as-of date is treated as unknown for that ticker (it cannot be on a list), so an old as-of date cannot be rebuilt after the fact: `TrendAnalysis` holds the latest row only.

Registered in `core/cron_health.py` (`CRON_JOB_NAMES`, a weekly cadence of 8 days before it reads overdue, `JOB_METADATA`; it is no longer in `DISABLED_CRON_JOBS`) and scheduled in
`crontab.txt`. The default as-of is the last completed XNYS session at the moment it starts: on a normal Saturday that is Friday's close, in a week with a Friday holiday (Good Friday, the
observed Independence Day) it is Thursday's, and after a half-day Friday it is that Friday (`tests/test_weekly_opportunity_snapshot.py` pins the five cases with the real calendar).

**Tracked-universe protection.** A ticker on a list of a run whose as-of date is within `OPPORTUNITY_PROTECTION_DAYS` (180) is in the universe with reason `opportunity`
(order: after `added`, before `browsed`): it is not dropped by the 30-day view expiry, and the wipe sees it as protected (`PROTECTION_OPPORTUNITY`), so its bars keep
refreshing for outcome tracking. A delisted flag still wins. See [Tracked universe](tracked-universe.md).

## API (read-only)

`GET /api/opportunities/dates` (every run, newest first, with the two list sizes), `GET /api/opportunities/latest`, `GET /api/opportunities/{as_of_date}` (404 when none).
The four Scorecard GETs (`/api/opportunities/scorecard{,/flags,/picks,/outcomes}`, below) are registered **before** the dated route. No POST/PUT/PATCH/DELETE exists (a test pins the route table). Rows come back exactly as stored (`OpportunityRowOut`), in list order: Momentum by composite momentum score,

## Row selection (2026-10-12)

Each table row has a `Checkbox` (neutral checked style, `aria-label` "Select <ticker>"); the header checkbox ("Select all shown") selects exactly the rows shown (current tab plus tier filter) and shows the indeterminate dash when only some of them are selected; clicking it when all are selected deselects the shown rows only. **Selection is held by ticker** (`selected` in `app/opportunities/page.tsx`): it survives the tier filter and the Momentum / Reversal tabs (a ticker is on one list per run, so it names one row), and is cleared when the snapshot date changes and after a successful Add to watchlist. Shift-click selects the range of shown rows from the last one clicked (to the state the clicked row is moving to); space on a focused checkbox toggles it. A checkbox click (and the padding of its cell) never triggers the row click or the new-tab ticker open. A fixed-height status line above the table (`h-8`, so nothing shifts) reads "12 selected" with a "Clear" text action, or a transient notice (5 s). No control is disabled: a control with nothing to act on answers when used.

- **Add to watchlist** acts only on the selected rows (both tabs, any tier, in the run's order), labelled "Add 12 to watchlist". With nothing selected it opens nothing, sends nothing and shows "Select at least one ticker" in the status line. The watchlist menu, its bulk confirm ("Add 12 selected tickers to ...?") and the add calls are the existing ones. The ETF-only list is offered only when every selected row is an ETF. After a successful add the selection is cleared and the line reads "Added 12 to “Growth”" (with "(n already there)" when the bulk call reports some). A single selected ticker uses the single-add call, so the menu shows Remove for a list that already holds it (the existing control, unchanged).
- **Pick rows** are written exactly as before, server-side, in the same request: the page sends `opportunity_run_id` of the run shown (the latest, or the selected past snapshot), the backend stores `(as_of_date, ticker)` for each submitted ticker that is a row of that run. A bulk add records every submitted ticker (including any the list already held, as since Phase 2a); a single add records only when it succeeds (409 records nothing); a pick failure never fails the add. Adding from any other page sends no run id and records no pick. No backend change.
- **Export** acts on the selected rows when there are any, otherwise on everything in the current view (tab plus tier filter), never on the whole weekly run. The trigger says which: "Export 12 selected" or "Export 55 shown". The formats are the existing ones (`buildTradingViewText` grouped by sector, with the exchange prefix; thinkorswim bare symbols, one per line). The file name is `opportunities-<list>-<selection|view>-<as_of_date>[_thinkorswim].<ext>`; a selection that spans both lists names both (`momentum-reversal`). With nothing to export the status line says "Nothing to export" and no file is written. There is no "export the whole weekly run" option.

## Outcome tracking (phase 2a, built 2026-10-12)

Whether each listed name later beat the market. Stored data only, no FMP call, no LLM. The Scorecard ("Scorecard", below) reads these tables and serves them read-only; nothing here writes for it. **Conventions (agreed):**

- **Price-only returns**, never dividend-adjusted (the basis of the sector performance and momentum lenses).
- **Entry is the first session's OPEN after the as-of date.** SPY's bar dates are the session calendar (holidays and half-days need no calendar of their own). Horizon N is the Nth bar after the entry bar, N = 5, 10, 20, 60; the exit is that bar's CLOSE. The entry bar is bar 1 of the position for the stop, `worst_move`, `best_move` and `max_drawdown` windows (the window is the entry bar through the horizon bar).
- **Stop: intraday, 10% below entry.** A bar's low <= 0.9 x entry is a stop hit, the entry bar's own low included. A gap below the stop fills at the open: `stop_fill_return = min(-10%, open / entry - 1)`. `forward_return` is the buy-and-hold return; the stop never changes it, it is recorded beside it. A stop is path-dependent and final: it is written as soon as it occurs, on every horizon row whose window contains it, while the horizon is still `pending`.
- **Benchmarks:** SPY is the headline (`spy_return`, `excess_vs_spy`, entry open to the same exit date's close); the ticker's own sector ETF (`SECTOR_TO_ETF` on the stored `TickerScore.sector`) is the second. An ETF, or a stock with no mapped sector ETF, has `sector_etf = null` and null sector fields: it is compared with SPY only.
- **Censored rows are excluded from means.** A horizon is `censored` when the ticker is missing the entry or the horizon bar and SPY is already more than `CENSOR_GRACE_SESSIONS` = 3 sessions past the horizon date; `censor_reason` is `delisted` (flagged), `left_universe` (no longer tracked) or `stale` (neither). The row still stores the return to the last available bar (`exit_date`, `exit_close`, `forward_return`) as a sensitivity line. A `complete` row is frozen and never recomputed. **Grace period:** a censored row stays revivable for `CENSOR_REVIVE_DAYS` = 14 calendar days from `first_censored_at` (the day it was first censored; the clock never restarts): the updater re-evaluates it on every run, and if the missing bars have appeared it becomes `pending` or `complete` again with `censor_reason` and `first_censored_at` cleared. A temporary price-data gap looks exactly like a delisting, so freezing at once would freeze a hole for ever. After the 14 days the row is frozen like a `complete` one, even if the data returns. A real delisting simply stays censored (re-evaluated, unchanged) until it freezes. A censored row with no `first_censored_at` (written before the column) is stamped at its next evaluation. Readers are unaffected: censored rows are still excluded from means and keep the sensitivity return; a revived row is no longer censored.
- **`entry_gap_pct`** is the entry open against the frozen as-of close; `entry_gap_flag` is true beyond 25% (a gap that large means the list's price was not the price anyone could pay).
- **The pool is stored, and its unlisted names are priced.** `OpportunityPoolRow` keeps every gate-passing ticker of each run, whether it was listed or not, so the listed names can be compared with the ones the rules left out. `OpportunityOutcome` has rows for the listed snapshot rows only; the unlisted pool names have slim `OpportunityPoolOutcome` rows (2026-10-12, see "Pool outcomes" below). The Scorecard serves both ("Scorecard", below).
- **Picks.** `OpportunityPick` records the names the user chose with the manual Add to watchlist action on the Weekly Routine page (the run shown, latest unless a past snapshot is selected), so a later scorecard can compare the user's picks with the lists. The action itself is unchanged. **A pick is keyed by `(as_of_date, ticker)`, not by run id, and nothing ever deletes one** (see "Picks" below).

Tables (insert-only, KEEP in the data registry, in the nightly backup): `OpportunityPoolRow` unique on `(run_id, ticker)`; `OpportunityOutcome` unique on `(run_id, ticker, horizon)`; `OpportunityPick` unique on `(as_of_date, ticker)` (no run id, no watchlist id: join to the run, snapshot and outcome rows through `as_of_date` plus `OpportunityRun.kind = 'weekly'`); `OpportunityOutcomeRun` (one row per updater run: its heartbeat-style result, and the SPY bar date it saw). Pure engine: `scoring/opportunity_outcomes.py`. Updater: `pipeline/opportunity_outcome_update.py` (scheduled nightly at 03:40 UTC, see "Scheduled" below).

**The weekly job and the pool.** `persist_run` writes the run, its snapshot rows and the pool in ONE transaction (`ComputedRun.pool`, built in `compute_run` from the same features: exactly the gate-passing tickers, so `pool_rows` equals `gate_passed`). The rules and `RULES_VERSION` are unchanged (the pool is not a rule). A rerun for an existing date is still a no-op that does not compute. **`--force`** deletes that run's snapshot, pool and outcome rows and inserts the replacement in the same transaction (a failed insert leaves everything as it was); the counts come back as `deleted`. **It never touches picks** (they are keyed by `as_of_date`, so a rebuilt run, which takes over the old run's id because sqlite reuses the highest id, neither deletes nor re-attaches them; first built keyed by run id and fixed 2026-10-12). The pool needs the as-of stage rows (`TrendAnalysis` holds the latest row only), so it can only be captured while the nightly trend job has not moved past that session; if the stage rows are gone the run refuses as before (the existing run, pool or not, is left untouched).

**The updater.** `uv run python -m pipeline.opportunity_outcome_update --once | --dry-run | --run-id N | --as-of D` from `backend/` (one of the four is required). Orchestration `data/opportunity_outcome_data.py::update_outcomes`; zero FMP calls (cache read only). Every listed snapshot row gets four outcome rows on the first run (seeded `pending` when it cannot be priced yet); only `pending` rows are recomputed, a pending row is written only when a value changed, and `complete` / `censored` rows are never touched. Only completed bars are used (a bar after the last completed session, or a last bar written before its own session's close, is dropped, SPY's included). SPY and the sector ETFs are read once, every other ticker in chunks of 60. A ticker that fails to read or price keeps its rows as they were (a failed bar read skips the whole chunk the same way) and the run is `partial`. A normal run is a **no-op unless SPY has a bar newer than the last run's** or a listed row has no outcome rows yet; `--run-id` / `--as-of` skip that check; `--dry-run` writes nothing. **Result record:** one `OpportunityOutcomeRun` row per real run (`running` -> `success` / `noop` / `partial` / `failure`, the message, the SPY bar date it saw, a JSON summary), the next run's source for "SPY has a new bar"; a partial run stores no SPY date so the next run retries. It sits beside the `CronRunLog` heartbeat (which the Scheduled Jobs page reads) because it carries the SPY bar date the no-op rule needs.

**Scheduled (2026-10-12).** `40 3 * * *` in `backend/crontab.txt`: every night at **03:40 UTC (11:40 Hong Kong)**, `-m pipeline.opportunity_outcome_update --once`, log `backend/logs/opportunity_outcome_update_cron.log`. The server clock is UTC. Timing evidence (CronRunLog, 10 nights to 2026-10-12): price-target ended by 03:20:10 at the latest, the 03:25 score recompute by 03:26:22, the 03:30 backup by **03:35:10** at the latest (usually 03:33), so 03:40 starts at least 4m50s after the last job of the chain. The updater itself is seconds (1.7-5 s on the first 79 rows; chunked reads, about 130 MB peak), and the Saturday weekly job starts at 04:00, 20 minutes later, so the two never overlap. Registered in `core/cron_health.py` (`CRON_JOB_NAMES`, daily cadence 36 h, `JOB_METADATA` "Prices the weekly opportunity lists' outcomes ... no FMP calls", 3:40 AM) and wrapped in `cron_heartbeat` (`run_scheduled` in the job file). **Heartbeat rules:** a result or a normal "no-op: SPY has no bar newer than ..." (weekends, market holidays, a night the bars did not move) is **success**, with the one-line message; an exception (no SPY bars, a crash) is **failure**; ticker-level failures are a `partial` run that stays green unless they pass `check_failure_threshold` (all attempted failed, or at least the rate limit of 25 or more attempted), which is **failure**. A dry run writes no heartbeat. `tests/test_cron_wiring.py` pins the slot (after the backup by 8+ minutes, 15+ minutes before the Saturday job). *Caveat:* a SPY cache that stops moving for days reads as a green no-op here; the nightly bar-cache job (1:05) and the stale-data checks are what flag that.

**Picks.** The Weekly Routine page passes the id of the run it shows to the existing Add to watchlist call (`opportunity_run_id` on `POST /api/watchlists/{id}/tickers` and `/tickers/bulk`); the same request then calls `data/opportunity_data.py::record_picks`, which resolves the run to its `as_of_date` and stores the pick under `(as_of_date, ticker)` (`picked_at`, `source` = `opportunities_page`; no watchlist id). A bulk add records every ticker submitted that is a row of that run (whether or not the list already held it); a single add records the ticker only when the add succeeds (a 409 for a ticker already on the list records nothing); a refused add (the ETF-only list, the cap) records nothing. Picking the same ticker again for the same `as_of_date` is a no-op (the first `picked_at` stays); from two different dates it is two picks. A run id the run table does not know, a ticker the run never listed, or a failing pick write is ignored and never fails the add. The latest run is the one sent unless a past snapshot is selected. **Nothing deletes a pick:** not `--force`, not removing the ticker from a watchlist, not deleting the watchlist, not the ticker leaving the universe or being wiped (`opportunitypick` is KEEP in the registry), not a deleted run (a pick whose `as_of_date` has no run is kept as is). Migration (2026-10-12): the table was first keyed by `(run_id, ticker)`; `core/db.py::_migrate_opportunity_pick_key` rebuilds such a table once, copying every pick with its run's `as_of_date` (a pick whose run is gone keeps the old table as `opportunitypick_unmapped` rather than being dropped). The live table was empty, so it was simply re-created.

## Daily flags (Phase 2b v1, built and scheduled 2026-10-12)

A daily routine on the frozen lists: for the names of the **latest** weekly run it looks for three triggers on the newest completed session and stores each hit. Stored data only (zero FMP calls), no LLM; the flags are read by the Scorecard ("Scorecard", below). Code: `scoring/opportunity_triggers.py` (pure rules), `data/opportunity_daily_data.py` (orchestration), `pipeline/opportunity_daily_flags.py` (job: `--once | --dry-run | --as-of D`), flag outcomes in `data/opportunity_flag_outcome_data.py`. Design basis: the Phase 2b investigation report; the eight recommendations in it are decided as written (docs/decisions.md, 2026-10-12).

**Triggers** (versioned apart from the list: `TRIGGERS_VERSION = "1"`, ids end `.v1`, `triggers_hash()`; the weekly `RULES_VERSION`/`rules_hash` and B3 are untouched. Change a trigger -> bump `TRIGGERS_VERSION` and the id):
- **`D1.entry_event.v1`**: a *stored* Warren `blue_up`/`yellow_up` or BB+RSI event dated after the list's as-of date (the kinds B3 reads). Reversal-list names, and Momentum-list names carrying the `deep_pullback` tag. **Monitored names only**; any other is *not covered*. The knowable-before-next-open test uses the event row's **`created_at`** (it must be at or before the open of the session after the event's own session), never the event date; an event written later is not flagged and is recorded as a `late_event` gap.
- **`D2.stage_upgrade.v1`**: the Weinstein stage moved up against the stage **frozen on the list row** (decline -> base, decline -> advance, base -> advance), or a pending Advance appeared that the list row did not have. Reversal-list names only. Top is never an upgrade.
- **`D3.pullback_to_ma.v1`**: `vs_ma_pct <= 5.0` (`PULLBACK_MAX_VS_MA_PCT`, fixed and versioned) while the stage is Advance, the MA slope is positive and Mansfield RS is above 0. Momentum-list names only. It is the literal condition, not a *crossing*: a name already within 5% on the list date flags the first night (`already_at_ma_on_list` is in the frozen inputs, so a scorecard can split them). On the 2026-10-09 list 4 of 55 Momentum rows qualified.

**Cohort rule.** Only the **latest weekly run's listed rows** are watched (the pool is never flagged). A flag on session S attaches to the latest run whose as-of date is **before** S, and only if that run lists the ticker. One flag per `(list_as_of_date, ticker, trigger_id)`: the first session it qualified (a rerun never duplicates). Consequences: at its slot on a Saturday (03:45, before the 04:00 weekly job) Friday's signals count against the *previous* list; Friday's own signals never count against the list built as of Friday (its B3 rule already read them), so the first session judged against a new list is the following Monday.

**Tables** (insert-only, KEEP in `data/ticker_data_registry.py`, in the nightly backup with no change):
- `OpportunityDailyFlag`: unique `(list_as_of_date, ticker, trigger_id)`; `list_name`, `tier`, `flag_date` (the session), `observed_at` (when written: the knowable-at time a pick is compared with), `close` (the session close, the entry-gap reference), `sector`, `trigger_version`, `inputs_json` (the list row's figures and what the trigger saw, **frozen at observation, never rebuilt**).
- `OpportunityDailyRun`: one row per real night (`running -> success | noop | failure`): session(s) evaluated, SPY bar seen, the weekly list judged against, upstream job status per session, watched/flags counts, and the three honest-denominator fields below.
- `OpportunityFlagOutcome`: unique `(flag_id, horizon)` (5/10/20/60), the columns of `OpportunityOutcome` plus `flag_id`, `trigger_id`, `flag_date`, `trigger_version`. `OpportunityPick` and `OpportunityOutcome` are not changed, and a pick is still keyed `(as_of_date, ticker)`: join a pick to flags through `list_as_of_date` and compare `picked_at` with `observed_at`.

**Not covered vs incomplete vs no flag** (kept apart so a scorecard's denominator is honest; all in `OpportunityDailyRun`):
- *not covered* (`not_covered_json`, `{trigger: [tickers]}`): D1 only; the name is not on a monitored watchlist, so the Warren / BB+RSI jobs never looked, even if an event row exists. Never "no flag". (2026-10-09 list: 12 of the 25 D1-eligible names.)
- *incomplete* (`incomplete_json`, `{trigger: {ticker: reason}}`): the trigger could not be judged tonight: an upstream job of that night did not succeed (`CronRunLog`: D1 needs 01:20 BB+RSI and 01:25 Warren, D2/D3 need the 01:05 trend job; the window is the session's close to the next session's close; `skipped` is not success), the name has **no final bar for the session** (the bars cache's provisional-bar test, the same one the weekly gate and the updater use), the stage row is not as of the session, there is no stage row, or its bars failed to read. Never "no flag".
- *no flag*: judged, did not fire. Not stored.

**Missed nights and gaps.** D1 catches up: every session after the job's own last-seen SPY bar is evaluated, each against its own cohort. D2/D3 read `TrendAnalysis`, which holds the latest row only, so they are judged **only on the newest completed session**; every other session in a catch-up, and an `--as-of` that is not the newest, records a `state_trigger_gap` (`gaps_json`). `late_event` gaps record D1 events that were not knowable in time.

**The job.** `uv run python -m pipeline.opportunity_daily_flags --once | --dry-run | --as-of YYYY-MM-DD` from `backend/`. A normal run is a **successful no-op** unless SPY has a completed bar newer than **this job's own** last-seen date (the newest `OpportunityDailyRun` with one; not the outcome updater's) or there is no weekly list dated before the session; `--as-of` skips the check. A no-op is green, an exception (no SPY bars, a crash) or read failures past `check_failure_threshold` are red, an *incomplete* trigger is not a failure, a dry run writes nothing (no flags, no log row, no heartbeat). Registered in `core/cron_health.py` (`CRON_JOB_NAMES`, 36 h cadence, `JOB_METADATA` "3:45 AM"), wrapped in `cron_heartbeat("pipeline.opportunity_daily_flags")`. First measured runs (79 listed rows): about 0.5 s of work, 2.3 s wall with the interpreter, peak RSS about 127 MB (chunks of 60 tickers).

**Flag outcomes.** The outcome updater (`pipeline.opportunity_outcome_update`, 03:40) also prices `OpportunityFlagOutcome` in the same invocation, with the same engine (`compute_outcomes`), the **flag session as the as-of date** and the flag's frozen close: entry is the next session's open, horizon N is the Nth bar after it, price-only, a 10% intraday stop recorded beside the return, SPY and sector-ETF benchmarks, censoring and the 14-day grace as for the weekly rows. The updater is the only writer of both outcome tables and the flag job writes flags only, so they cannot double-count. The weekly path (`update_outcomes`) is unchanged; with no flags the updater's behaviour and message are exactly as before; the flag part has its own no-op test (it also runs when a flag has no outcome rows yet, so a flag written at 03:45 is seeded at the next 03:40 run, once its entry bar exists).

**Scheduled (2026-10-12).** `45 3 * * *` in `backend/crontab.txt`: every night at **03:45 UTC (11:45 Hong Kong)**, `-m pipeline.opportunity_daily_flags --once`, log `backend/logs/opportunity_daily_flags_cron.log`. The server clock is UTC. It is 5 minutes after the 03:40 outcome updater (which prices the flags written the night before) and 15 minutes before the Saturday 04:00 weekly job; the 01:05 bar/trend job, 01:20 BB+RSI and 01:25 Warren jobs have long finished, and the 03:30 backup ended by 03:35:10 at the latest. The `DISABLED_CRON_JOBS` entry is removed; the job is in `CRON_JOB_NAMES`, the daily 36 h cadence and `JOB_METADATA` ("3:45 AM"), and `tests/test_cron_wiring.py` pins the order (after the updater, after the backup by 8+ minutes, 15+ minutes before the Saturday job). **Heartbeat rules:** a no-op ("SPY has no bar newer than ...", "no weekly opportunity list dated before ...") is green; an exception or read failures past `check_failure_threshold` are red; an *incomplete* trigger is not a failure. **Check a run:** the Settings > Status row and `SELECT * FROM opportunitydailyrun ORDER BY id DESC LIMIT 3;`. **Disable again:** comment the crontab line, add a `DISABLED_CRON_JOBS` entry, `crontab crontab.txt` from `backend/`, check `crontab -l`. ## Pool outcomes (scorecard step 1, built 2026-10-12)

The baseline a scorecard compares the listed names with: how the pool names the rules **left out** did over the same horizons. Stored data only (zero FMP calls), no LLM, **served read-only by the Scorecard since 2026-10-20** ("Scorecard", below). Code: `scoring/opportunity_pool_outcomes.py` (a thin pure wrapper over the unchanged engine), `data/opportunity_pool_outcome_data.py` (orchestration), the third step of `pipeline/opportunity_outcome_update.py`. This supersedes the "baseline computed on the fly" idea of the Phase 2b decision 8: reading about 500 tickers' bars per request costs about 12 s and 130 MB, so the nightly updater prices them once and stores the result (docs/decisions.md, 2026-10-12, "Scorecard step 1").

- **Which names.** Every `OpportunityPoolRow` with `listed = false` of a weekly run (516 of the 595 pool names of the 2026-10-09 run). Listed names already have `OpportunityOutcome` and are never repeated. Four rows per name (horizons 5 / 10 / 20 / 60).
- **Same conventions as the lists, same engine.** `scoring/opportunity_outcomes.py::compute_outcomes` is called unchanged with the run's as-of date and the pool row's frozen close: entry is the first session's OPEN after the as-of date, horizon N exits at the Nth bar's CLOSE, price-only, SPY headline and sector ETF second (SPY only for ETFs and unmapped sectors), `entry_gap_pct` against the frozen close with the 25% flag, censoring after `CENSOR_GRACE_SESSIONS`, and the 14-day revive grace from `first_censored_at`. A `complete` row is frozen. The wrapper keeps only the slim fields; the stop, best/worst move, drawdown and exit close the engine also computes are dropped.
- **`OpportunityPoolOutcome`** (insert/update by the updater only; KEEP in `data/ticker_data_registry.py`; in the nightly backup with no change, which copies the whole database): unique on `(run_id, ticker, horizon)`. Columns: `run_id`, `ticker`, `horizon`, `status` (pending / complete / censored), `censor_reason`, `tier`, `assigned_list`, `leveraged`, `entry_date`, `entry_open`, `entry_gap_pct`, `entry_gap_flag`, `exit_date`, `forward_return`, `spy_return`, `excess_vs_spy`, `sector_etf`, `sector_return`, `excess_vs_sector`, `rules_version`, `provenance` ("live"), `computed_at`, `first_censored_at`. `tier`, `assigned_list` and `leveraged` are copied from the pool row when the outcome row is first written (the baseline is matched to the listed names without a join).
- **`assigned_list`** is what the frozen trend stage allowed (`scoring/opportunity_rules.py::assign_list`, the single router, with `FRESH_ADVANCE_MAX_WEEKS`): the weekly job already stores it on every `OpportunityPoolRow` (`momentum`, `reversal`, or null for Top, no fresh stage row and an Advance of unknown age), so nothing is derived again. A null is context only: the stage allowed neither list. `leveraged` is the pool row's frozen `leverage` (2 or 3) as a boolean.
- **Retroactive.** The pool is frozen with its run and the daily bars are cached, so any run's pool is priceable at any time after its entry bar exists; the first real run prices the 2026-10-09 pool (all rows `pending` until Monday 2026-10-12 has a stored bar).
- **The updater.** The pool is priced after the weekly and flag-outcome steps in the same `--once` invocation (`update_pool_into` merges the result the way the flag part does). Existing outcome behaviour, rows, keys and tests are unchanged. A normal run is a no-op unless SPY has a bar newer than the last run's or a pool name has no outcome rows yet; `--run-id` / `--as-of` target one run. Only runs with open or missing rows are loaded, complete rows are held as keys, bars are read in chunks of 60 and each chunk's row objects are released after its commit. `--force` on the weekly job deletes the run's pool outcomes with its snapshot, pool and outcome rows (they are keyed by run id).
- **Message and heartbeat.** The `OpportunityOutcomeRun` / `CronRunLog` message gains `; pool outcomes: N name(s), complete x, pending y, censored z; a created, b updated` **only when a run has an unlisted pool** (the existing messages, with no pool rows, are unchanged), and the run summary gains a `pool` key. Pool tickers that fail count in the same `attempted` / `failed` totals and the same `check_failure_threshold`; a no-op stays green and a failed ticker leaves its rows as they were.
- **Measured (2026-10-12, read-only against the stored bars).** First retroactive pricing of the 2026-10-09 pool: 516 names, 2,064 rows, **6.1 s, peak RSS 139 MB** (112 MB is the bare interpreter and pandas). Simulated steady state, 13 weekly cohorts of that pool all open at once (about 6,700 name-runs): **about 55-60 s, peak RSS about 163 MB**, which is the whole updater's worst case a quarter from now, under the 2-minute budget. Growth: about 2,060 rows per weekly run, about **107,000 rows a year** (about 20 MB with indexes, on a 1.4 GB database).
- **Honest limits.** The unlisted names carry no `opportunity` tracked-universe protection: 447 of the 516 are index members and most of the rest are watchlist / manual / added tickers, so few can lapse, but a lapsed name's rows are censored `left_universe` and excluded from baseline means, which biases a baseline slightly upward. Extending the 180-day protection to the pool is deferred.

**Deferred** (decided, not built): breakout from a base, a daily-bar RSI pivot-low, liquidity-zone and MA-reclaim triggers, invalidation flags (stage to Top/Decline, RS below 0), closing the coverage gap for listed names (Phase 2c), flags for the pool, a pick tied to a specific flag. (The scorecard UI/API was built 2026-10-20; what it defers is listed in its own section.)

## Scorecard (built 2026-10-20)

What happened to the frozen lists afterwards, as a **read-only** aggregate of the stored outcome tables: no schema change, no new table or column, no crontab or pipeline change, no write, no FMP call. The outcome engine, the updater and the flag job are untouched. Code: `scoring/opportunity_scorecard.py` (pure functions, no DB), `data/opportunity_scorecard_data.py` (reads one weekly cohort at a time, in-process cache), the four GETs in `core/main.py`, `frontend/components/opportunities/ScorecardView.tsx`, `frontend/lib/scorecard.ts`. Decisions: docs/decisions.md, 2026-10-12 ("Scorecard step 1") and 2026-10-20 ("Scorecard built").

**Endpoints** (all `viewer`-readable, write-free, registered before `/api/opportunities/{as_of_date}` or that route would capture "scorecard" and answer 422; `tests/test_opportunity_scorecard_api.py` pins the order, GET-only and zero writes). Every one takes `rules_version` (default: the current `RULES_VERSION`); `scorecard` and `flags` also take `triggers_version` (default: current `TRIGGERS_VERSION`) and `weights_version` (default: all).
- `GET /api/opportunities/scorecard`: groups for all four horizons (5/10/20/60) and both benchmarks (SPY, sector ETF) in one response, the selected and available versions, the latest data date (`latest.outcomes_spy_bar`), the cohorts with their weights version and, per pending horizon, the **expected data date** (the session whose bar completes it: the (N+1)th session after the as-of date), `next_expected`, and the exclusion counts.
- `GET /api/opportunities/scorecard/flags`: per trigger (D1, D2, D3) eligible, flagged, not covered (D1 only), incomplete, unflagged, windows open, the cells, the D3 split by `already_at_ma_on_list`, the deduped "any flag" view, and the per-name **ledger**.
- `GET /api/opportunities/scorecard/picks`: the count of picks and a proxy; an empty state while there are none.
- `GET /api/opportunities/scorecard/outcomes`: the row-level audit (`source` = listed | flags | pool, optional `horizon`, `limit` up to 20,000, `offset`), each row with the bucket it was counted in.

**Groups.** The list (Momentum, Reversal), then the tier within it (Quality, Momentum-only, ETF), then the list's **leveraged ETFs as their own row** (only when one was listed; never in an ETF tier or list figure), then the **rule cuts** B1, B2, B3 and `deep_pullback`. Rule cuts overlap each other and the lists, so each is computed on its own, is never summed and has no pool baseline. The list-level row is the list as a whole (all tiers but leveraged); tiers are never pooled across lists.

**A cell** is one group at one horizon against one benchmark. Every row falls in exactly one bucket, checked in this order: `entry_gap` (the entry open more than 25% from the frozen close, whatever the status), `pending`, `censored`, then `complete`; a complete row with no benchmark return (an ETF against its sector ETF) is counted as `no_benchmark`. Only `complete` rows with a benchmark return enter any figure. Every cell carries `n_complete`, `n_pending`, `n_censored`, `n_entry_gap`, `n_no_benchmark`, `cohorts` (weekly lists with a complete row) and `cohorts_total`.

**Statistics** are taken **per cohort first** (one weekly list; its names overlap the next list's), then summarised across cohorts: the headline is the **median of the cohort medians** of excess (return minus the benchmark's return over the same dates), beside the mean over all rows, the share of rows above the benchmark, "k of m cohorts positive" (cohorts whose own median excess is above zero) and the benchmark's own median return. Also: the **pool baseline** (the unlisted pool names with the same stage-assigned list and tier, the same statistics) and **listed minus pool** (the median over cohorts of the paired difference), the stop-hit rate (complete rows only), the **with-stop return** (derived, never stored: `stop_fill_return` if the stop was hit, else `forward_return`), the median worst move and drawdown, and an **"including censored" sensitivity line** (the censored rows at their stored last-bar return).

**The gate.** Values only with at least **20 complete rows and at least 3 cohorts**; labelled **Early** until **60 rows and 8 cohorts**; below the gate the cell carries counts only (`values` null), the table draws "—" and a "Too early" pill. The cohort count is the binding condition. The pool's figures stay hidden while the listed cell is below the gate.

**Exclusions, each with its count:** pending, censored, entry-gap rows and leveraged ETFs (a separate row) are counted on every cell; rows of another `RULES_VERSION` / `TRIGGERS_VERSION` are excluded by the version selectors (default: current) and counted in `excluded`.

**Weights versions.** The Quality tier depends on the score weights, which can change between lists (the 2026-10-09 list is weights v8, the 2026-10-16 list v9). The filter defaults to all and cells are **not split**; any cell holding Quality rows from more than one weights version carries `mixed_weights` and `weights_versions`, and the table draws a "Mixed weights" note. Picking one version keeps only that version's lists.

**Flags.** Flag results are priced from the flag date (entry the next session's open) and are never mixed with list results. Per trigger: *eligible* = the list rows the trigger applies to (`applicable_triggers`), leveraged funds removed; *not covered* (D1 only) and *incomplete* come from `OpportunityDailyRun` (the union over every night judged against that list; a name incomplete on any night stays out unless it flagged) and are **kept out of the denominator**; *unflagged* = eligible minus flagged minus not covered minus incomplete. The comparator is the same list's unflagged names priced **from the list date**, labelled **"Not a controlled comparison"**, and provisional while the list's flag window is open (the latest weekly list is the only open one). A flag with no outcome rows yet is counted as `n_unpriced`. Triggers are never summed; "any flag" keeps each name's first flag (earliest date, then trigger order). Flag aggregates are gated like the rest and will stay below the gate for months, so the main flag view is the **ledger** (ticker, trigger, list, flag date, return, excess, stop at the selected horizon) with no averages.

**Picks.** Proxy-priced from the **list date** (the list's own outcome row for the picked name), labelled "Priced from the list date, not your add date"; a pick whose list has no run is counted as unmatched. No picks exist yet (the table is empty), so the page shows one line.

**Cache and cost.** The three aggregate endpoints are cached in-process keyed on the latest `OpportunityOutcomeRun` id, the latest `OpportunityDailyRun` id and the weekly run table (plus the pick count for picks); the audit endpoint pages and is not cached. One computation at a time (a lock), cohort by cohort, with running totals and one small summary per cohort, so memory stays flat as lists accumulate. Measured on the live database through a read-only connection (2026-10-20, 2 lists, 178 listed rows, 4,052 pool rows): cold 0.53 s (most of it the first load of the exchange calendar for the expected dates), warm about 1 ms, about +20 MB peak RSS over the imported modules for all four endpoints.

**The page.** Under the Scorecard tab: an early-data banner whose dates come from the response; segmented controls for the horizon (sessions after entry) and the benchmark; weights, rules and triggers version selectors; one hairline table (mono tabular numbers, explicit sign, "—" when missing, `n` with its pending / censored / entry-gap counts on every cell, an "incl. censored" sub-line, a Quality "Mixed weights" note); the flag counts and ledger; one line for picks; an outline **Export CSV** (the table, long format) and **Export outcomes CSV** (the row-level audit, listed plus flags); the "Informational only" footnote and a price-only-returns footnote. Tier wording follows the tab ("Technical only" under Reversal, "Momentum-only" under Momentum; the stored key stays `momentum_only`). Excess is coloured green/red only on a cell past Early; below the gate and while Early it is drawn neutral. Never shown: "beats the market" / "works" wording, p-values, rankings or a best-rule highlight, equity curves, alpha, annualised figures, pooled horizons or tiers.

**Deferred (decided, not built):** a controlled flag comparison (state-based triggers cannot be rebuilt from stored data), a full picks section (needs picks), a cohort-by-cohort chart, bootstrap intervals, flag badges on the list rows, extending the 180-day `opportunity` tracked-universe protection to the unlisted pool, and a close-only stop (the stop stays the intraday 10% rule).
