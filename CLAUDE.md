# CLAUDE.md — Fathom

## What this is

Fathom is a company fundamentals valuation web app. It runs a multi-step fundamental screen on any US-listed ticker. The automated Analysis framework has 4 steps -- **Financials (Revenue, income and cash flow)**, **Growth Rate (Positive growth rate)**, **Profitability (Profitable and operationally efficient)**, and **Debt (Conservative debt)** -- combined into a **Fundamentals score** (weighted blend, unrounded; `scoring/weights.py::DEFAULT_WEIGHTS` are the defaults, Financials 30 / Debt 30 / Growth 20 / Profitability 20, user-adjustable in Settings > Score weighting and saved in `ScoreWeightSettings`) that a manually-set **Economic Moat** rating then **multiplies** (Wide 1.0; Narrow 0.85 by default, adjustable in Settings > Economic moat, saved in `MoatScoreConfig`; No moat **or not rated** 0.70, fixed): **Overall = round(Fundamentals score x Moat multiplier)**, rounded once, no cap, no hard-fail override (`scoring/overall.py`). A ticker with no Moat is scored as No moat and the UI says so. `TickerScore` stores `steps_score` (unrounded), `moat_multiplier` and `formula_version` beside `overall_score`. The defaults quoted in the docs are the code's; the saved set in the DB can differ.

- **`SCORE_FORMULA_VERSION` (`scoring/overall.py`) must be bumped whenever the Overall arithmetic changes or a step's scoring changes**, so stored rows are stale (a row on another formula or an older `weights_version` shows the header re-score and the Screener note). Saving or resetting the weights, saving the Narrow multiplier or the Screener recompute button starts a background full recompute (`pipeline/score_recompute_job.py`). The Python and TypeScript (`frontend/lib/overallScore.ts`) implementations share `backend/tests/fixtures/overall_verdict_cases.json`, regenerated by `backend/tests/fixtures/generate_overall_verdict_cases.py`.
- **"Fail" is retired as a display word:** every surface draws a stored verdict `"Fail"` as **"May not pass"** (`frontend/lib/tierColor.ts::verdictDisplay`; the Debt card draws a stored Step 5 `Pass with caution` as "Pass, ratio in breach", `debtVerdictDisplay`). The stored/internal key stays `"Fail"` everywhere (DB, API, fixtures): `toneFor` and every comparison run on the raw value, never on the relabelled word. Overall "Pass with caution" is a label only (score, sort and `SCORE_FORMULA_VERSION` unchanged).
- **Valuation** (`backend/data/step3_data.py` / `backend/scoring/step3.py`) is a separate, fully-implemented "Valuation" tab with its own DCF/DDM/P-B/PSG method selection -- it is **not** part of the Overall blend (no `step3` key in `STEP_WEIGHTS`).
- A ticker whose profile says `isEtf`/`isFund` gets the ETF page variant instead of the stock tabs and scoring, and `get_summary` skips every stock-only FMP fetch for it (docs/specs/etf-page.md).
- The Debt (Step 5) and Step 1 by-company-type rules, the Pass-with-caution rule, the Screener Overall filter and the version history are in docs/specs/overview.md, debt.md, financials.md, company-type-variations.md and docs/decisions.md (2026-10-07, 2026-10-08).

## Tech stack

- **Frontend**: Next.js (App Router), TypeScript, Tailwind v4, shadcn/ui (`base-lyra` style, phosphor icons, neutral base color). Dark-only theme — no light mode toggle, `dark` class hardcoded on `<html>` in `app/layout.tsx`. SWR for data fetching. Mirrors the visual style and conventions of the sibling `options_tracker` project.
- **Backend**: Python (>=3.12), FastAPI, SQLModel, pandas/numpy for any data manipulation — favor vectorised operations over row-wise loops. Dependency management via `uv` (`uv run`, `uv sync`).

## Running the app

`./bin/start.sh` from the repo root brings up both servers in **dev mode by default** (preflight checks, explicit `init_db()`, an FMP connectivity check, then `uvicorn --reload` + `next dev` with hot reload, each in its own process group); `./bin/start.sh --prod` (or `FATHOM_MODE=prod`) instead does a `next build` and runs both in production mode — lower memory, but no hot reload, so code changes need a stop/start — see `backend/OPS_RUNBOOK.md`'s "Starting / stopping the app" section for what success/failure look like. `./bin/stop.sh` stops both, safe to run anytime including when nothing is running.

## Folder layout

`bin/` start/stop scripts; `frontend/` Next.js app; `backend/` FastAPI app in packages by role: `core/` (entrypoint `core.main:app`, models, db, schemas, config, cache, cron_health, data_groups), `clients/` (FMP/SEC clients, bar caches), `helpers/` (calc helpers), `data/` (per-tab `get_stepN_data` orchestration), `scoring/` (pure scoring functions, `weights.py`), `analysis/` (research modules), `scrapers/` (index lists), `pipeline/` (cron/maintenance entrypoints that read/write the real DB; `backfills/` is one-time scripts), `scripts/` (ad-hoc research that never touches production data), `tests/` (pytest, mirrors the layout via import paths). Full package-by-package layout: docs/backend-layout.md.

Every cron entry in `crontab.txt` invokes its script as `-m package.module` (e.g. `uv run python -m pipeline.nightly_fundamentals_fetch`), never a bare script path: a script run as `python pipeline/foo.py` puts its own directory on `sys.path` and fails with `ModuleNotFoundError` on its sibling imports. Run `-m` with `backend/` as the working directory. The app itself runs as `uv run uvicorn core.main:app`, not `main:app`.

## Data source

[Financial Modeling Prep (FMP)](https://financialmodelingprep.com) (paid tier) is the **sole** data source for fundamentals, company classification, and Fundamentals 1-5/Overall Assessment scoring, via `backend/clients/fmp_client.py`. FMP is the **only** external data source for everything, price/OHLCV bars included, with no fallback provider anywhere. (SEC EDGAR, `clients/sec_edgar.py`, remains only as a fundamentals cross-check source, not a market-data one.) See docs/specs/fmp-data-and-bar-cache.md.

## Watchlists

Each watchlist is capped at `WATCHLIST_CAPACITY` (100 tickers, `backend/core/main.py`): adding past the cap is rejected with an explanatory error, never silently truncated. A watchlist named `E<positive integer>` (`E1`, `E10`, ...) or exactly `ETF` is **monitored**: the Liquidity Zone, BB+RSI and Warren nightly jobs read the deduped union of every such list (case-sensitive full match, no leading zeros; `E0`, `E01`, `e1`, `ETFs`, `W1` are NOT monitored), minus delisted-flagged tickers. The rule is defined once, in `data/watchlists.py` (`MONITORED_WATCHLIST_PATTERN`, `is_monitored_watchlist_name`, `list_monitored_tickers`): **never re-declare the pattern in a job** (`tests/test_watchlists.py` fails if one does). **The "ETF" list is ETF-only and permanent:** a ticker may join it only if it is a known ETF, enforced for every add path by the one helper `data/watchlists.py::tickers_not_allowed_on_watchlist` (HTTP 400); it cannot be renamed or deleted, and no other list can be renamed or created as a case/whitespace variant of it. Never re-implement either rule at a call site. Mechanism, the ETF table, the add endpoints and load numbers: docs/specs/watchlists.md, docs/specs/etf-page.md.

## Tracked universe (which tickers the nightly jobs process)

Defined once, in `backend/data/tracked_universe.py::load_tracked_universe` (the stock side of `partition_known_tickers`; ETFs have their own, `load_etf_universe`). **Opt-in:** a page view does not admit a ticker. Every known ticker gets ONE reason, first match in the order `delisted`, `index`, `watchlist`, `system`, `manual`, `added`, `browsed`, `expired`, `untracked`; the last three are not in the universe, keep all their data, and are only candidates for the wipe (`pipeline/wipe_untouched_tickers.py`: dry run by default, `--apply` locked behind `FATHOM_ALLOW_WIPE_APPLY=1`, not scheduled). A delisted flag removes a ticker from every job at once. **Never re-declare the union in a job or call a removed name** (`tests/test_tracked_universe.py` fails if one does); `SYSTEM_TICKERS` does not exist, do not reintroduce it. `load_all_known_tickers` is the wide set for the non-US purge, the delisted sync, the search fallback and the backfills. Detail: docs/specs/tracked-universe.md; operations (verify, back up, roll back): `backend/OPS_RUNBOOK.md`, "Tracked universe".

## Caching policy

Fundamentals change infrequently, so raw FMP pulls are cached in a local SQLite database (`backend/core/models.py::FundamentalsCache`, via SQLModel) keyed by `(ticker, statement_type, period)`, with a `fetched_at` timestamp on each row. Before refetching from FMP, check whether a cached entry is fresher than the configurable staleness window — `Settings.cache_staleness_days` in `backend/core/config.py`, default 7 days, overridable via the `CACHE_STALENESS_DAYS` env var. Never hardcode the staleness window at a call site.

### History protection

A cached statement row is a whole FMP response, so it is **never overwritten by a shorter one**: every `FundamentalsCache` write goes through `core/cache.py::_write_cache_row` (the single write path for `get_or_fetch`, `get_or_fetch_earnings_aware` and `force_fetch`) and the one merge rule in `core/history_merge.py` for the keys in `HISTORY_KEYS` (new rows replace cached rows for the same period, cached older periods the answer lacks are kept, and an empty, null, error or non-list body never replaces a non-empty row). **A new cached statement type must be added to `HISTORY_KEYS` or `SNAPSHOT_STATEMENT_TYPES`** (`tests/test_history_merge.py` fails otherwise). The Refresh button keeps history rows and marks them stale (`INVALIDATED_AT`) instead of deleting them; the shared bars cache's replace path keeps the older bars when FMP answers with less history. Read-only audit: `uv run python -m pipeline.cache_history_audit`. Detail: docs/specs/fmp-data-and-bar-cache.md, "History protection"; docs/specs/statement-data-quality.md.

### Data groups: pausing FMP (per-group toggles)

FMP on/off is per **data group**, stored in the DB (`core/data_groups.py`) and edited live from Settings > FMP data groups, with no restart; there is no global env flag (only `FMP_API_KEY`/`FMP_BASE_URL` are read from `.env`). A group that is off, above the plan, or restricted is **cache-only**: the last cached row is served (even if stale), nothing is ever wiped, and the nightly jobs that depend on it report a real `skipped` cron status.

- **Single gate.** `FMPClient.get` maps each endpoint to a group (`ENDPOINT_GROUP`) and `core/cache.py` maps each cached `statement_type` (`STATEMENT_TYPE_GROUP`). **A new FMP endpoint or cached statement type must be added to those mappings** (`tests/test_data_groups_registry.py` fails if any used one is unmapped; an unmapped endpoint fails closed). Never call a bulk/batch endpoint (it needs the Ultimate tier; the same test pins that none is used).
- A 402 never disables a group on a symbol-scoped failure (canary-confirmed only), and for the `fundamentals` group restricts one request variant, not the group (`VARIANT_GROUPS`).
- Tests get a fresh in-memory group config per test (`conftest._isolate_data_groups_engine`); a test wanting an off state calls `core.data_groups.set_master`/`set_group_enabled`. `pipeline/nightly_score_recompute.py` is cache-only throughout and makes zero FMP calls whatever the group state.
- No `insider` data group exists (the feature was shelved and removed); do not reintroduce it without an explicit decision.

Everything else (group list and tiers, effective state, master switch, what degrades when a group is off, the refresh 503 rule, the 402 safety net, API/UI): docs/specs/fmp-data-and-bar-cache.md, "Data groups: pausing FMP"; `backend/OPS_RUNBOOK.md`.

### Ad-hoc reproduction scripts must not touch the real database

`backend/fathom.db` is the one real database (`config.py` has no test/real split), and `cache.get_or_fetch` persists whatever `fmp_client` returns into whatever `engine` is bound. Any one-off script (or test) that reproduces behavior against real ticker data by monkeypatching `fmp_client` **must** first construct a fresh in-memory engine and monkeypatch it onto **every module's own `engine` reference** (each data-layer module has its own `Session(engine)` import, so patching one does not patch another); never monkeypatch `fmp_client` alone against the default `db.engine` (this contaminated production twice, 2026-07-28 and 2026-08-04). A session-scoped write-guard in `backend/tests/conftest.py` raises on any write to the real engine, so a missing patch fails loudly in CI; a second autouse guard (`_forbid_real_http`) blocks real outbound HTTP the same way, so a test that reaches FMP must mock the client method. `pipeline/audit_fixture_contamination.py` (read-only) scans for the fingerprint weekly. Incident history: docs/archive/claude-md-history-features.md.

## Cron job heartbeat / health monitoring

`core/cron_health.py::cron_heartbeat("<job_name>")` wraps every real cron job's entry point (`if __name__ == "__main__":`) and writes a `CronRunLog` row however the job ends; it is purely additive and never alters the job's real outcome. **`CRON_JOB_NAMES` in `core/cron_health.py` is the single source of truth for which cron jobs exist:** a new job added to `crontab.txt` needs a matching `CRON_JOB_NAMES` entry, an `_EXPECTED_CADENCE_HOURS` entry, and a `cron_heartbeat(...)` call at its own entry point, or it ships unmonitored (`backend/tests/test_cron_wiring.py` fails if they drift apart). **Editing `crontab.txt` alone changes nothing on the running box:** reinstall it (`crontab crontab.txt` from `backend/`) and check `crontab -l` against the file, or a job silently never runs on the new schedule. A job that reports attempted/failed counts calls `check_failure_threshold` from its `record_outcome` rather than hand-rolling a rule. A deliberately disabled job (its `crontab.txt` line commented out) is listed in `DISABLED_CRON_JOBS`; **`pipeline.nightly_corporate_events` has been disabled since 2026-10-01** (about 1,165 FMP calls per run, over Starter's 300/min): the Chart E/D markers serve the frozen cache; re-enable = uncomment the cron line at its planned slot **1:50 AM** (it must end before fundamentals starts at 2:00) + delete the `DISABLED_CRON_JOBS` entry + update `JOB_METADATA` + `crontab crontab.txt` from `backend/` (docs/specs/corporate-events.md, docs/decisions.md 2026-10-01). Mechanism, cadence windows, interrupted runs and the failure threshold: `backend/OPS_RUNBOOK.md`, "Cron job heartbeat / health monitoring".

## Company classification

`classify_company_type` (`backend/scoring/classification.py`) drives Bank/REIT/Insurance/Utility/Property-Developer detection, including several manually-verified non-lender ticker overrides (sector/industry text alone can't reliably distinguish a genuine lender from a non-lender in some categories) and the requirement that "Bank" treatment implies genuine CET1/NPL-reporting capability, not just lending activity. See docs/specs/company-type-variations.md for the current tables and mechanism.

## Workflow rules

- **Testing scales with what changed.** Frontend changes always run the full vitest plus typecheck and lint. Backend changes run targeted tests when isolated (one scoring function, endpoint or job) and the full suite when a shared file changes: `conftest` or fixtures, models/schema/db migrations, shared helpers (the cache layer, the FMP client, the universe loaders), scoring constants / `SCORE_FORMULA_VERSION` / weights, or the cron registries. Docs-only changes run no tests. Run the full backend suite once before any push.
- **Plan Mode by default.** Propose a plan and wait for confirmation before writing code for each phase.
- **Confirm before committing.** Stop and confirm with the user before committing each phase's work, and again before pushing — push only after explicit confirmation.
- **One commit per logical change.**
- Never use `--dangerously-skip-permissions`.
- **No browser-based verification after a code change.** This environment can't drive a browser — rely on `tsc`, `eslint`, and the test suite instead of visually checking the result.
- **Clean up after yourself.** Delete any temporary files, scratch scripts, or processes you started, before ending a task.
- **Design and product decisions live in `docs/design-system.md`, `docs/design-system-charts.md`, and `docs/decisions.md`.** Check these before styling anything or proposing a new UI pattern — don't re-derive a decision that's already been made.
- **`docs/design-system.md` is authoritative for visual style** (fonts, sentence case, dark-only, no theme toggle) and overrides any conflicting style guidance in the generic skills under `.claude/skills/` (`frontend-design`, `ui-styling`, `design-system`, `ui-ux-pro-max`).
